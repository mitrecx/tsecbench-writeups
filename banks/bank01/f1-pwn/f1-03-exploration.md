# f1-03 · 探索记录

对应题解：[`f1-03.md`](./f1-03.md)

## 目标与起点

服务自称模拟 TLS heartbeat：可以设置载荷，再按一个调用者给的长度回显。先用 `DUMP` 看它记录的长度，再用大于载荷的 `HEARTBEAT` 看回显会不会越过缓冲。

## 第一阶段：短的过度读取只有 0，4096 之后才是 flag

`SETPAYLOAD hi` 回 `250 set 2 bytes`。`HEARTBEAT 512` 回 `250 512 bytes:`，内容是 `hi` 和 510 个 0。`HEARTBEAT 4096` 仍然只有开头的 `hi`，后面全是 0，响应里没有 `flag{`。

`SETPAYLOAD` 300 个 `B` 时，`DUMP` 的 `payload_len` 是 300，`HEARTBEAT 300` 也只回这些 `B`。缓冲至少能装下 300 字节，短的声明长度不会读到缓冲外面。

把声明长度加到 20000 之后，非 0 字节从偏移 4096 开始，一共 42 字节，内容是 flag。

## 走不通 / 走过的弯路（留档）

| 方向 | 结果 | 判据 |
| --- | --- | --- |
| `HEARTBEAT 512` | 只有 0 | 回显长度 512，除了载荷没有别的非 0 字节 |
| `HEARTBEAT 4096` | 仍然只有 0 | 响应长度 4129，非 0 区域只有开头的 `hi` |
| `HEARTBEAT` 等于刚写入的 300 | 没有越界 | 回显就是那 300 个 `B` |
| `HEARTBEAT 20000` | 读到 flag | 偏移 4096 处是 `flag{...}`，前面 4096 字节是载荷和 0 |

## 这次真正的收获

载荷缓冲是 4096 字节。`HEARTBEAT` 相信声明长度，所以要申请比 4096 更长的回显，flag 才出现在缓冲后面。
