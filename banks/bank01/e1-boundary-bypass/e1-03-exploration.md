# e1-03 · 探索记录

对应题解：[`e1-03.md`](./e1-03.md)

## 目标与起点

诊断面板把输入框里的字符串拿去执行，入口还有一套自定义过滤。占位符是 `ping 127.0.0.1`，所以第一下就按提示提交，看过滤落在边界还是落在命令本身。

## 第一阶段：403 和命令输出不是同一种失败

`ping 127.0.0.1` 的响应是 nginx 的 403 页，长度 153 字节左右，页面上没有诊断面板的 `<pre>`。`echo hello` 则回到原来的诊断页，`<pre>` 里是 `hello`。

这把两层拆开了：403 是边界关键字，200 且 `<pre>` 有内容才是命令真的跑了。后面每个 payload 都按这个判据记。

## 走不通 / 走过的弯路（留档）

| 方向 | 结果 | 判据 |
| --- | --- | --- |
| `ping 127.0.0.1` | 边界拦截 | 403，正文是 nginx Forbidden，没有 `<pre>` |
| `id`、`whoami`、`ls /challenge` | 边界拦截 | 同样的 403 页 |
| `cat /challenge/flag1.txt` | 边界拦截 | 403。flag 路径本身没有特殊，拦的是 `cat` |
| `/bin/cat /challenge/flag1.txt` | 边界拦截 | 绝对路径躲不过关键字 |
| `echo hello` | 命令执行 | `<pre>` 内容是 `hello` |
| `head` / `tac` / `nl` 读 flag 文件 | 读到 flag | 这三个名字不在表里，`<pre>` 直接是 flag 文本 |
| `c''at`、`c""at`、`ca\t` | 读到同一份 flag | 403 消失，说明边界匹配的是连续的 `cat`；shell 还原引号和反斜杠之后命令仍然是 `cat` |

## 这次真正的收获

过滤在 nginx 前面，不在 shell 里。它认的是命令名的连续写法，不认 shell 引号。关键字表漏了 `head`、`tac`、`nl`，所以读文件不必先绕过 `cat`。flag 在 `/challenge/flag1.txt`。
